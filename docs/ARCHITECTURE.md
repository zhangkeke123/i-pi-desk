### 为什么agent 必须单独一个进程
1. **不阻塞UI**：prompt 组装、token 流、工具执行都是重活，放主进程会卡住窗口事件循环「2. **可崩可重启*：agent 跑飞（OOM、死循环）时只重启sidecar，主进程和会话数据不受影响「3. **可替换*：sidecar 只暴露线协议。将来把内核换成服务端编排（Java 控制面），主进程一行不改」4. **可独立调话*：`node dist/sidecar.js` 就能跑，不需要起 Electron、
> 关键不变式：**Renderer 不碰 fs，Main 不跑 agent，Sidecar 不碰窗口」* 三条线任何一条被跨越，后面都要还债「

## 4. 协议契约

### 4.1 Renderer →Main

通道命名 `desk:<domain>/<action>`，常量集中在 `packages/shared/src/ipc.ts`、
**所有invoke 一律返回`Result<T>`**，
```ts
type Result<T> = { ok: true; data: T } | { ok: false; error: AppError }
```

不用「抛异常」的原因：Electron 跨进程会把Error 序列化得堆栈与自定义字段全丢，错误码传不到 UI。信封是唯一能让 UI 做「按码分支」的形态」
### 4.2 Main →Sidecar

stdio 上的 **NDJSON**（一行一帧），JSON-RPC 2.0 的简化子集「
```jsonc
// 请求
{ "id": "1", "method": "session.prompt", "params": { ... } }
// 应答
{ "id": "1", "result": { ... } }
{ "id": "1", "error": { "code": "PROVIDER_AUTH", "message": "401" } }
// 单向通知（无 id，{ "method": "agent.event", "params": { "sessionId": "...", "event": { ... } } }
```

**硬约束：日志只能写stderr、* sidecar 的stdout 是协议流，往里写一行`console.log`
就会让主进程的解析器吃到一帧垃圾「
### 4.3 AgentEvent（归一化事件）

UI 只认这套事件，`pi` 的原生事件在 `translate.ts` 里被翻译过来，
| 事件 | 含义 |
|---|---|
| `run.started` | 一次run 开始|
| `text.delta` / `reasoning.delta` | 流式正文 / 思维链|
| `tool.started` / `tool.finished` | 工具调用生命周期 |
| `approval.requested` | 危险工具请求裁决（UI 弹卡片） |
| `usage` | token / 花费 |
| `message.committed` | 一条消息定稿（用于持久化） |
| `run.finished` / `run.failed` | run 结束 |

**为什么要有这一层*：pi-* 的事件名与结构会随版本变。把它挡在sidecar 内部，UI 和持久化格式就不会被上游的破坏性升级带着起——这正是「内核可替换」的落地方式」

## 5. 数据与落盘
```
<userData>/
├─ settings.json      # AppSettings + provider 列表（不含任何明文密钥）
├─ secrets.json       # safeStorage 加密后的 provider key（密文，难OS 用户绑定，├─ workspaces.json    # 最近打开的工作目录├─ sessions/          # 一个会话一个JSON，sessionId>.json
├─ pi-agent/          # pi 内核自己的状态目录（见5.2，└─ logs/
```

### 5.1 三条规则

1. **单一 owner**：只有主进程能碰这些文件。sidecar 要持久化就通过事件回传，让主进程写「2. **密钥与设置分离*：`settings.json` 可以随便备份/同步，`secrets.json` 不行」   用Electron `safeStorage`（Windows DPAPI / macOS Keychain）加密，密文一OS 用户绑定「   系统没有可用密钥环时**拒绝保存**并明确告知，绝不静默降级成明文」3. **消息增量内*：`message.committed` 事件到达即落库，而不是等 run 结束 ——   否则用户聊了半小时崩一次，全丢」
> **第一版不用SQLite**：`better-sqlite3` 是原生模块，要走 electron-rebuild，> ABI 不匹配会变成「装不上 / 打包后崩」两类难查故障。单机场景下会话数据里> 远达不到需要数据库的规模「*换SQLite 的时有*：单会话消息 > 1 万条）> 或需要全文检索。届时只替换 `store/json-store.ts` 的实现，上层接口不变」
### 5.2 内核状态必须关起来（实测踩过）

pi 默认把状态写在`~/.pi/agent`、*实测一次`createAgentSession()` 就会**，
- 创建 `<agentDir>/auth.json`、`<agentDir>/models-store.json`
- `mkdir` 出`<agentDir>/sessions/--<编码后的 cwd>--/`，首条消息落 `.jsonl`
- 启用 `grep` / `find` 时把 `rg` / `fd` **下载到`<agentDir>/bin/`**

直接用它默认值有三个后果：往用户 home 塞文件（卸载留垃圾）、和用户自己装的
pi CLI 抢同一件`auth.json`、以及内核状态与我们自己的数据混在一起」
所以sidecar 启动时必须做全这四件事，缺一不可，
```ts
process.env.PI_CODING_AGENT_DIR = agentDir              // →<userData>/pi-agent
process.env.PI_CODING_AGENT_SESSION_DIR = <agentDir>/sessions
// createAgentSession 时：
settingsManager: SettingsManager.inMemory()
sessionManager: SessionManager.inMemory()
```

cwd 侧不会建 `.pi/`，这一点无需处理「

### 5.3 重启后恢复上下文（「模型失忆」问题）

会话消息由主进程落盘，而内核的 `SessionManager` 是`inMemory` 的「两者放在一起就会出现一个很别扭的状态：

> **界面上历史都在，模型却完全不记得「*

用户打开昨天的会话追问一句「继续改刚才那个函数」，得到的是「哪个函数？」。这不是边缘情况，而是**每天第一次打开应用必然发生**的事「
修法是把落盘历史**喂回内核**（`packages/agent-host/src/history.ts`）：
主进程在每次 prompt 时附上该会话的落盘消息，sidecar 只在**为某会话新建内核会话时*
采用它（之后内核自己就是最新的，再灌一次会让同一段对话在上下文里出现两遍）。
每次 prompt 都附、由 sidecar 决定用不用，而不是「主进程只发第一次」：
主进程并不知道sidecar 内部是否已有该会话的内核状态——sidecar 崩溃重启后，
主进程那个「已经发过」的标记就会失真，结果就是又一次失忆「**让状态的所有者做决定**比让另一方猜可靠「
#### 三个必须做对的细节（都由测试抓出来）

**一、只重放文本，丢掉工具调用」*

工具调用与工具结果在多数厂商协议里是**成对**的：有`tool_calls` 就必须有对应的`tool` 结果，否则直接400，而且各家报错各不相同。配对关系一旦被截断
（超过上限、或某条消息在崩溃中丢了），重放就会**让整个会话再也发不出请求**。
而用户真正在意的是「模型记得我们聊过什么」，助手正文通常已经概括了它做过什么」代价写清楚：模型不记得工具调用的原始细节（具体diff、命令输出）——需要时它应当重新读文件，这也符合「磁盘才是真相」的原则「
**二、必须合并相邻的同角色消息」*

丢掉「只有工具调用、没有正文」的 assistant 消息后，原本 `user →assistant(工具) →user`
会变成`user →user`。OpenAI 兼容接口通常容忍，但 **Anthropic 的Messages API
明确要求 user/assistant 交替**，会直接 400，且报错不会告诉你原因「
**三、历史不能以 user 结尾」*

总会有「问了但没得到回复」的落盘消息：用户提问后关掉应用，或那一轮因为模型端不可达而失败（失败时不会产用assistant 消息）。留着它，重放后紧跟本次新提问
就又是`user, user`。这种悬挂提问本身没有信息量 ——用户马上会重新问一遍「
#### 裁剪

默认重放最近40 条、不超过 60k 字符（条数与字符双上限）。冷启动第一轮不该因为历史很长而变得非常贵；从最近往前保留，
并保证至少保留最后一条（否则「消息本身超预算」会让历史完全为空）。
### 5.4 窗口尺寸与位置的记忆

`window-state.json` 记窗口矩形与最大化状态。这件事本身很小，但**不做的话每天都会碰到一次*（调好窗口、换个显示器、或者习惯把窗口贴在右侧窄条里，重启全白费「
#### 真正需要小心的地方：恢复一个「已经不存在的位置」
直接存什么位置就用什么位置是危险的：用户拔掉外接显示器后，上次保存的坐标可能
完全落在不存在的屏幕一——窗口会*在屏幕外打开**，表现为「点了图标没反应」。这是这类功能最常见的翻车方式」
所以保存的矩形必须一*当前某块屏幕的可视区域*有足够重叠（80×80 像素），
否则放弃位置、保留尺寸，让Electron 自己居中」
只80 而不是「完整可见」是有意的：用户刻意把窗口拖到只露一条角是合理用法；
但只剩几个像素就等于「用户抓不到窗口」，必须搬回来」
判定逻辑放在 `store/window-bounds.ts`）*不import 任何 Electron API** 的纯函数），
因此可以被node 直接跑测试——而它恰好是唯一有真实后果的部分。持久化在`store/window-state.ts`。这条分层不是洁癖：第一版把两者写在一个文件里，测试一跑就撞上 `paths.ts` 里的 `electron.app`，根本跑不起来」
#### 两个必须处理的细节
- **最大化时不能记最大化后的尺寸「* 最大化状态下 `getBounds()` 返回铺满屏幕的矩形，
  存下来之后用户取消最大化就再也回不到原来的大小。所以记 `getNormalBounds()`、- **只在退出时写是不够的「* 强杀（任务管理器、崩溃）不触发`close`，位置就丢了」  所以拖动结束也写一次（节流 500ms），退出时再写一次兜底「  节流是必须的：拖窗口时`resize` 事件能产生几百次，每次都写盘既浪费又伤磁盘「
#### 验证

单测 15 条覆盖判定规则（拔屏后位置丢弃、多屏保留、露一角保留、只剩一条缝丢弃「脏数据回退、最大化透传）。端到端另有一条走**正常关闭**路径（`window.close()` →断言文件被写出（强杀不会触发这个钩子）→ 改写成有辨识度的尺寸 →重启 →断言窗口按它打开」
> 端到端验的是 1040×720，实测恢复成 **1041×721** ——窗口边框各占 1 像素「> 所以断言用±2 容差：精确相等会把平台差异当成功能缺陷「


### 5.5 一条消息只能有一份：重复落库与重复渲染
这一节记的是一个*长期隐藏的真实缺陷*，以及它的通用教训「
#### 现象

聊天区里用户消息出现 **3 次*、助手消息出现**2 次*；会话文件里用户消息也存了2 份「功能看起来「正常」（内容都在），所以只看功能的自测全绿 ——它是我在做「输入框历史」时顺带暴露的：历史里同一条消息出现多遍，翻上一条看不出变化「
#### 两条叠加的重复
**一、主进程把用户消息落库了两次」*

用户消息在调用内核*之前**就`persistAndAnnounce` 了一次——这是刻意的：
模型还没回应就崩掉时，用户输入不该丢。但**内核也会把这条用户消息作一`message.committed` 回显**，于是同一个消息又被落库、又被广播「
**二、渲染层有两条通道都在往同一个数组里追加「*

- 会话的`message` 事件（主进程落库后广播）
- agent 的`message.committed` 事件（流式事件的终点，
这两条覆盖同一件事。它们到达的先后**没有保证**，所以「谁负责追加」必须只有一个答案「
#### 修法

- 主进程：`message.committed` 里*按角色跳过用户消息* ——主进程只创建用户消息）  其余消息都来自内核，这个判据既简单又不会漂移「- 渲染层：**以落库的会话为消息的唯一真相**。追加只发生在会话`message` 事件里；
  agent 的`message.committed` 不再追加（它仍然负责其它运行状态）。
顺带一个细节：`live`（流式态）的清空与「把定稿消息加进列表」必须在**同一个`set`** 里完成「分成两个通道做就会出现「streaming 已清空、定稿消息还没到」的一帧闪烁「
#### 教训

**只断言「内容在不在」是不够的，还要断言「有几份」。*
`includes(...)` 这类断言对重复完全免疑——而重复正是最容易被忽略「又最容易被用户一眼看穿的那类缺陷。现在聊天区与落库两侧都有条数断言「

### 5.6 同一件事有两个写入方时，必须让结果与顺序无关

§5.5 那个「消息被落库两次」不是孤侧——顺着同一类问题查了一遍，
会话列表上有一个*同源的竞态*，
- 主进程在 `session.create` 里广播`created`）- `newSession()` 拿到返回值后又显式插入一次（保留它是有意的：万一批广播早了  渲染层订阅而丢掉，列表仍然是对的）。
两条路径改同一份列表，而*到达顺序没有保证**：广播早到则被后面的显式插入覆盖（正常），广播晚到则列表里出现两份同一个会话（React 还会因为 key 重复而告警）。它一直没暴露，只是因为事件通常早于 invoke 的返回值到达——那是运气，不是保证」
修法是*去重**而不是删掉某一条：`[event.session, ...sessions.filter(s => s.id !== event.session.id)]`、两条路径都留着，但结果与顺序无关「
#### 一条可以复用的判据

> 只要同一份状态有两个写入方，就要问：**交换它们的顺序，结果还一样吗：*
> 不一样就是潜在缺陷，而且它通常只在负载高或时序变化时才现形 ——> 测试跑一百遍可能全是绿的「
顺带清掉了一处*没人后*的广播：`provider-changed` 曾发在*会话**通道上，
而渲染层保存 provider 后自己就把返回值写进了 store。一条没有消费方的广播不只是无用 ——它会让后来的人以为「改 provider 会自动同步到界面」。死代码当删则删「

### 5.7 同一件事在两处计算，就会分叉

§5.5 是「两个写入方」，§5.6 是「顺序敏感」。这里是同一族的第三种形态：

#### 现象：中止之后，界面不说「已中止」

#### 成因：两处判据不一样
| 位置 | 判据 |
|---|---|
| `translate.ts` 的`run.finished` | `event.aborted ? 'aborted' : 'end_turn'` |
| `runtime.ts` 的`prompt()` 返回值| `providerError ? 'error' : settledAborted ? 'aborted' : 'end_turn'` |

1. 两处**用同一条判据*：`settledAborted || aborted`。并且在两个文件里互相注是   「必须与另一处一致」——因为它们是两段代码，注释是唯一能把它们绑在一起的东西」2. 中止优先了provider 报错：`aborted ? 'aborted' : providerError ? 'error' : 'end_turn'`）   并且 `run.failed` 的早退分支也要跳过已中止的 run、
#### 最值得记的一点：它是**间歇性*失败的

provider 的错误能不能赶在 pi 判定 settle 之前到达，取决于时序 ——有时 `settledAborted` 先成立（判对），有时 `providerError` 先成立（判错）。

而是产品里存在两个可能的结果」* 一个稳定通过的断言不会暴露这种 bug，一个时红时绿的断言恰恰在说「这里有两个分支」，值得顺着查下去」

### 7.2 审批必须按会话记住（否则切走一次就再也批不了）

#### 现象

### 7.3 「允许并记住」到底记住了什么
#### 一句夸大的文案

审批卡片上那个按钮原来写着**「本会话始终允许「*。而白名单的键是：

```ts
`${toolName}:${JSON.stringify(args)}`     // agent-host 的approvalFingerprint
```

也就是说：*参数只要有一点不同就会再问一次*。而写文件几乎每次内容都不一样（内容就是参数），所以用户点完「本会话始终允许」，下一次照样弹卡片「
从用户视角看只有两种解释：按钮坏了，或者我刚才点错了。两种都会让他不再信任这个按钮、真相是第三种的：**这句话夸大了实际授予的范围*。
#### 处理方式：把文案改准，而不是把范围放宽

三个选项里选的是最保守的那个：

| 选项 | 为什么不 |
|---|---|
| 放宽到「同一工具在本会话内不再询问」| 对`bash` 是危险的：一次点击= 本会话内**所有*命令放行 |
| 放宽到「同一文件」| 对write/edit 合理且有用，但需要按路径取键，且取不到路径时必须**回落到精确参数*（绝不能回落到「全部放行」）。那是一次权限边界的改动，值得单独做，不该顺手塞进一次文案修正|
| **把文案改出*（选了这个，| 行为不变（更安全的方向），用户知道自己在授权什么|

所以按钮现在写「本会话内始终允许（相同参数）」，`title` 里再解释一遍；
「已处理」的回执也写成「始终允许此操作（参数相同的调用不再询问）」。
#### 怎么验的：两半，缺一不可

1. **文案**：卡片上能找到那个说清范围的按钮并点下去；回执里出现「参数相同的调用不再询问」。2. **行为与文案一致*：紧接着再发一轮（参数必然不同，因为夹具每次写入带递增序号），
   **必须再问一次*。
第2 条是这一节的核心：将来*放宽**范围时它会立刻变红，提醒同步改文档——也就是说，它守的不是「现在的行为」，而是「文案与行为不许分叉」。
#### 两个工具层面的教训
**①观察一个转瞬即逝的状态，要用 MutationObserver 而不是轮询「*

「已处理：…」这句话只存在于「裁决之后、本轮收尾之前」——而`run.finished` 会清空`live`、假模型几毫秒就跑完「执行工具→第二轮回话」，窗口比一次轮询间隔还短：
150ms 轮询看不到，25ms 轮询**偶尔**看得到「
> 一个「偶尔失败」的断言比没有断言更糟 ——下次它红的时候，没人知道是真回归还是抖动」
换`MutationObserver` 之后这件事变得确定：它按 DOM 变更触发，只要那句话真的渲染过一帧，
就一定被看到「
**①一个永远失败的守卫等于没有守卫「*

那个「模板字符串里的注释写了反引号」的扫描脚本，之前会把*已转也*的写法也报出来，
于是永远有1 条噪声、退出码永远是1。我因此**忽略了它报的「 处可疑行」*（然后真的写出了语法错误（同一类错误这一轮又犯了两次）。
现在它只报未转义的，退出码 0/1 就是真信只——面0 一律当阻塞处理「
### 7.4 白名单的生命周期：会话级、内存里、不跨进程
上一节把「允许并记住」的**范围**说清楚了（同一工具 + 完全相同的参数）。这一节回答另外三个问题——它们都只是读代码读出来的，端到端从没验过，
| 问题 | 答案 | 为什么这是安全性质 |
|---|---|---|
| 同一会话里同样的调用，第二次还问吗？ | **不问** | 这是这个功能存在的理由|
| 在A 会话授权，B 会话里同样的调用呢？ | **要问** | 白名单要是跑到全局，用户会以为「我只在这段对话里点过一次」|
| sidecar 重启后（哪怕同一个会话id）呢，| **要问** | 白名单要是不小心落了盘，一次点击会变成永久的放行|

后两条尤其重要：**它们失效时不会报错，只会表现为「它怎么没问我？」* ——一个不会自己暴露的洞。所以它们值得被固定成断言「
#### 怎么验的：自己起一个「参数恒定」的假模型
E2E 那套夹具**验不了*这件事：它每次写入都带递增序号（`#1`、`#2`…），参数永远不同，而「记住」的前提恰恰是*参数完全相同**。
所以这个自测（`verify-allow-always.mjs`）自己起了一个参数恒定的 OpenAI 兼容假模型，
直驱 `AgentRuntime`（不同Electron），四轮，
1. 会话 A：写一次→审批 →**允许并记但* →工具执行、文件落盘；
2. 会话 A：再来一次参数完全相同的调用 →**没有审批事件**，但工具**仍然成功执行**（3. 会话 B：同样的调用 →**重新问*（4. **文runtime**（ sidecar 重启） **同一个会话id**：同样的调用 →**重新问*。
第2 轮那条「工具仍然成功执行」是必需的：只知道「没问」是不够的——如果实现是「命中白名单就静默拒绝」，那同样不会问，而工具根本没跑「
另外有一条*对照组*：断言第1 轮与第3 轮收到的参数**逐字相同**。少了它，「第 2 轮没问」有可能只是参数碰巧不同造成的假象「
#### 写这个自测时踩的两个坑（都不是产品缺陷，但很值得记）

**①每轮都要有时限」* 第一版没有上限，于是某一轮挂住时整个自测**静静地停在那里*（既没有失败也没有结论，日志停在半个小标题后面。加一60 秒上限后，它第一次跑就把一个「等滚5 分钟审批超时」的场景变成了一条60 秒的失败 + 现场日志「
**①`writeEvent` 绑在 runtime 上，不是每一轮「* 第一版给每一轮发一个sink 数组，但事件只会进 runtime 创建时给的那个数组——于是「第 2 轮的工具结果」永远是 undefined，表现成一条*看起来像产品缺陷的失败*（「工具没成功执行」）。真相是脚手架自己拿错了数组。这也是为什么那条断言会写 `ok === true` 而不是只断言「没问」：
**它把脚手架的错误也一起暴露了出来**，只是需要我愿意去看它到底在说什么」
> 一条断言红了，第一反应不该是「改了哪行产品代码」，
> 而应该是「它到底观察到了什么」——这一次的答案是「我什么也没观察到」。
### 7.5 拒绝之后，模型看到了什么
权限模型里有一件事**只能由内核决定*：闸门返回`{ block: true, reason: "— }` 之后，那句 reason 到底有没有作为工具结果回给模型。我们的注释写着「会」——但那不是我们能决定的「

#### 抓到的真洞：`rm -fr` 一`rm -r -f` 会被静默执行

原正则要求递归标志出现在强制标志*之前**，
```

```

```

扫一眼分不清结构。现在引这CM6，把「能改」升级成「改得舒服」：
高亮、括号匹配、自动缩进、撤销历史、搜索、折叠、补全「
#### 三个决定值得记下来
**一、语言包按需加载**（`import()`），而*这条决定被推翻过一次*，过程值得留着「
拆包前主 chunk 是2.74 MB，其一417 KB 是各语言的Lezer 语法包——一次编辑只用一种，
但主 chunk 必须在首帧前解析完，等于每次启动都为用不到的语言付费「
第一版*刻意没做**，理由是：Vite 会切出独立chunk，而打包后的Electron 件`file://`

后来敢做了，不是因为风险消失了，而是因为**先有了验证能力*，
- 渲染层产物用相对路径（`./assets/...`，electron-vite 的`base` 默认值），  动态chunk 因此能按 `import.meta.url` 解析，- `verify:packaged` 会真的在生产档下打开编辑器并断言高亮生效 ——  **高亮生效本身就证明了语言 chunk 件`file://` 加载成功**。
结果：主 chunk 2.74 MB →**2.33 MB**，切出8 个按需 chunk（合记417 KB），
而总量几乎不变，752 KB vs 2742 KB）——说明没有重复打包，赢的是首帧解析时间「
> 顺序很重要：**先有验证能力，再做优化*。反过来做，就只能靠「我觉得应该没问题」发布「
**二、快捷键只能有一个来源「*

CM6 支持结`Mod-s`，对话框的window 监听也处理Ctrl+S。两边都留的话，
一次按键会触发**两次保存**：第二次带着已经过期的`expectedRevision`，必然被拒绝，用户看到的是莫名其妙的「文件已被外部修改」。
所以`CodeEditor` **刻意不绑定保存键**，只管编辑；快捷键由宿主统一处理「附带好处是焦点不在编辑器里时（点过标题栏、刚切只读）也能保存、`verify:renderer` 里有一条走真实按键的Ctrl+S 断言守着这个决定「
**三、颜色全部走 CSS 变量「*

编辑器主题与高亮样式都取 `var(--color-syn-*)`，切主题时编辑器跟着变，
不需要重建编辑器、也不用维护两套配色。浅色主题下的语法配色单独调这——暗色那套放在白底上对比度不足（注释与字符串尤其明显）。

- 编辑器可能在 chunk 到位前就被销毁（用户很快关掉对话框）→必须挡住迟到的事务，
  否则会对一个已经`destroy` 的view 派发更新，- `path` 可能在中途变化（用户又打开了另一个文件）→同样要挡住旧结果）  否则会给新文件套上旧语言的高亮「

「按需加载」这个优化*没有行为症状**：如果有人把 `import()` 改回静态`import`）功能完全正常，只是主 chunk 悄悄涨回 400 KB ——没有任何功能测试会红」

### 8.7 文件树操作：新建 / 重命名/ 移动 / 删除

#### 为什么移动做成「选择器」而不是拖拽
拖拽在Electron + CDP 一*无法可靠驱动**（合成drag 事件与真实指针行为差别很大），而移动是**破坏性操作* ——一个验不了的破坏性操作不值得做。所以做成可点可按的目录选择器：列当前目录的子目录、可一路往上级走、一个「移到这里」。
这也是「先有验证能力，再做优化/功能」在功能选择上的应用，**验证不了的东西，宁可换一种实现方式，而不是先做出来再想办法验「*

#### 移动比改名多的四个坑（都在`moveInWorkspace` 里）

改名只换名字、父目录不变，所以目标目录天然合法；**移动换的正是父目录*（于是目标目录必须完整过一遍工作区校验。四个坑，
1. **目标目录也可能越界「* 不校验的话，「移动到 `../../`」就是一个   绕过读取防护的*写入原语** ——这一条比读越界更严重「2. **目录不能移进它自己的子孙里*（如把`src` 移到 `src/lib`）。   某些实现会先建链接再递归，结果是**整棵子树从工作区里「消失「*（还在，但按路径不可达）。   用`realpath` 比较，避免软链绕过」3. **不能覆盖「* 与改名同理：`renameSync` 在POSIX 上会静默覆盖同名文件」4. **源与目标相同要报错，而不是假装成功」* 用户停在原目录点「移到这里」时，   告诉他「已经在这个目录里了」比假装成功更有用」
失败时*留在选择器里**（不收起），与新建失败时的处理一致——收起会让人以为操作成功了」

工作区面板第一版是只读的（标+ 预览），建文件只能靠 agent 或外部编辑器、补上这三个操作后，「在工作区里自己动手」这件事才算闭环「
#### 三条安全线（都在主进程，渲染层仍然拿不到绝对路径，
**一、新建：父目录必须已存在「*

自动创建多层目录意味着要一边创建一边校验「新目录仍在工作区内」，
而中间层可能已经有软链——那是一条容易写错的路径。当前UI 也只需要「在选中的目录里建一个文件」，所以先不做「
创建用`writeFileSync(..., { flag: 'wx' })`：前面虽然查过一次「是否存在」，
但那是「检查后使用」，两次之间可能有别人创建了同名文件。用 `wx` 让内核来保证原子性「
**二、重命名：只接受单个名字（跨目录移动是单独的操作）。*

`newName` 必须是单个名字（同`/`、`\`、`.`、`..` 一律拒绝）。否则「改名」就变成了「移动到任意位置」，而目标目录完全没有经过工作区校验「
跨目录移动*没有并进改名**，而是单独一个`moveInWorkspace`（见 §8.7）——因为它换的正是父目录，目标目录必须完整过一遍校验，两者的防线并不相同「把「改名」做成能带路径的形式，等于给一条已经被验证透的路径开一个后门「
目标已存在时**拒绝而不是覆盖*：`renameSync` 在POSIX 上会**静默覆盖**同名文件 ——用户改个名字却弄丢了另一个文件，这是不可接受的。Windows 上它会报错，

**三、删除：进系统回收站，不是`rm`、*

编辑器里的误删应该可恢复，而「永久删除」在 UI 上一次点击就发生，代价不对等。所以走 `shell.trashItem`。删除动作*作为参数注入** `removeInWorkspace`，一旦在该文件里 import electron，这个模块就没法用node 直接跑测试了
（`verify-workspace-fs.ts` 正是这么跑的）——而这里恰好最需要测试」校验逻辑（越界、根目录、存在性）留在原处，那才是要测的东西」
#### 界面上的三个选择

- **行内操作悬停才出现*。常驻会让整棵树变得很长很吵，而这三件事都不是高频到  需要一直可见。目录多一个「在此新建文件」。- **删除确认就地展开在行下方**，而不是弹窗：目标就在上一行，用户能直接确认  「我删的是这个」；弹窗反而会遮住它。确认文案里明说「会移到系统回收站」。- **新建后直接打开**。建完文件的下一步几乎一定是写点东西」- **失败时留在输入态并显示原因**。收起输入框会让人以为操作成功了」

### 8.8 发送失败时不该丢失已输入的内容

输入框是**先清空再发送*的——这是必需的，因为一轮run 可能跑几分钟，不能等它结束才清空。但发送可能*在落库之前*就失败（没配 provider、缺 key、provider 被删），
这时内容就白丢了：用户刚敲了一大段，回车之后什么都没发生，还得重新敲一遍「
修法是失败时把内容还回输入框，而*判断依据不是错误码清单，而是证据**，
> 主进程在调用内核**之前**就落库并广播用户消息，但上述校验发生在落库*之前**。> 所以「会话里有没有这条消息」正好区分了两类失败」
- 校验失败 →会话里没有这条消息→内容还给用户，- 内核或网络失败→会话里已经有这条消息 →**不能**还原，否则会和历史重复」
只看最后一条消息即可（发送时它一定追加在末尾）。
用错误码清单也能做，但那要把「哪些码发生在落库前」这份知识复制到渲染层，
而它随时可能漂移「*用可见的状态去判断，比用一张需要维护的清单更可靠「*

还有一条不能省的细节：用户可能在失败后已经重新打了一段，
这时**不要覆盖件* ——宁可丢掉我们这份「

### 8.9 会话删除：与文件树保持同一种「问一句「
删除会话是*误点代价最高*的一处：两个 24px 的小图标只在悬停时出现、还紧挨着，点错丢掉的就是一整次对话。而它原先**连确认都没有** ——文件树的删除却是有确认的「

现在的做法与文件树一致：确认**就地展开在这一行里**（不弹窗，目标就在眼前），**鼠标离开这一行即撤销** ——与「操作按钮只在悬停时出现」是同一套直觉「
### 8.10 输入框历史记录（上下键）

上下键翻阅*当前会话**里发过的用户消息。实现上刻意**不另存一份历史*，
> 历史 = 这个会话里已经发过的用户消息（`role === 'user'`）。
好处是重启后自动还在（会话消息本来就持久化）、也不会出现「历史列表与真实对话不一致」。代价是历史以会话为界 ——但那正是人们期望的语义「
三个刻意的细节：

- **只在单行输入时生效*。多行输入里上下键属于光标移动，抢走它会让  「在中间某行改一个字」变得很难受「- **翻到最旧一条就停住，不绕回最文*。绕回会让人分不清自己翻到哪了」- **进入历史前把当前草稿存入 ref，翻回底部时还给件*。  否则按一下上键再按一下下键，正在写的东西就没了——这是最容易漏掉的一条「

### 9.5 一个只在渲染层存在的坑：默认provider 的*副本**

## 10. 插件机制

插件是*可执行代码*，与技能（声明式、不执行）是两个量级的东西。完整manifest 契约一校验规则解[`packages/shared/src/plugin.ts`](../packages/shared/src/plugin.ts)「
### 10.1 形态：独立子进程+ 工具代理

```
agent-host（sidecar）  └─ PluginHost
       ├─ spawn(plugin-runner.mjs) →插件子进程（NDJSON over stdio）       └─ 把插件声明的工具注册这pi session（customTools + tools 白名单）
```

插件作者只写一个普通ESM 模块，
```js
export async function activate(ctx) {}
export const tools = { async my_tool(args, ctx) { return '结果' } }
```

协议、JSON 帧、stdout 纪律都由我们的`plugin-runner.mjs` 负责「**这是刻意的*：与其在文档里要求作者「别用console.log」，不如在运行器里把
`console` 重定向成日志通知 ——让正确的做法成为默认，而不是靠约束」
### 10.2 我们承诺什么、不承诺什么
| | 事实 |
|---|---|
| **不承诺OS 级沙箱* | 子进程拥有与应用同级的系统权限。上游也没有沙箱。我们不假装有「|
| **承诺进程隔离** | 插件崩溃/内存泄漏不会带走 agent 会话；插件不能读我们内存里的 provider 密钥「|
| **承诺最小环境变里* | 子进程*不继批* `process.env`，只拿白名单（PATH / SystemRoot / TEMP …）。这是这里唯一**实质态*的运行时保护 ——用户 shell 里的令牌、代理凭据、CI 密钥不会顺手流进插件」|
| **`permissions` 是声明不是开具* | 它的用途是**知情同意**（启用界面读的就是它）与审计，不是技术拦截。因此有一条硬规则：*未知权限必须报错，不能静默忽略* ——静默忽略会让同意界面少列一项，那比没有声明更糟，因为它制造了虚假的安全感「|

由此推出两个产品决定，
1. **安装后默认不启用」* 「启用」这个动作就是同意发生的地方。装完自动跑起来）   等于那份权限声明从来没被谁看过」2. **启用界面上权限清单直接放在按钮旁边*，不折叠进详情「
### 10.3 一条安全相关的校验规则

插件工具名*不得占用内置工具名*（`read`/`write`/`edit`/`bash`/…）。
原因不是「会报错」，恰恰相反：注册优先级是`扩展 > customTools > 内置`，所以一个插件只要声明`bash`，就能在用户毫不知情的情况下**替换掉真正执行命令的那个工具**。这是命名空间冲突带来的安全后果，必须在安装时拦住」
### 10.4 被测试抓到的两个真实缺陷

**缺陷一：`customTools` ≈已生效」*

`createAgentSession({ customTools })` 只是把工具*注册**进去。实测：注册之后
`getActiveToolNames()` 里仍然只有内置工具——因为传了 `tools` 数组时，
pi 会跳过「自动激活新注册工具」那条分支。修法是把插件工具名并进生效集合「
**缺陷二（更隐蔽）：`tools` 数组同时是白名单」*

`tools` 不只表示「初始生效集」，它同时是 `allowedToolNames`。不在其中的工具会被
**直接从工具定义表里过滤掉** ——连注册都不会发生「
于是现象变成了：「插件已激活、它的技能也进了系统提示，但工具对模型不可见」。从现象几乎不可能反推到「因为`tools` 是白名单」。这条由
`verify:renderer` 里「插件工具已被注册给内核」的断言抓出来，
现在代码里那行注释记着这个坑「
> 两个缺陷都不是实现疏忽，而是**对第三方 API 语义的误到*。> 这也说明为什么「注册了」和「生效了」必须分成两条断言 ——> 只测前者会一路绿灯「
### 10.5 验证方式（三层）

| 层| 命令 | 证明什么|
|---|---|---|
| 契约 | `pnpm --filter @i-pi-desk/shared test`）6 条） | manifest 校验规则，含「未知权限被拒」「占用内置工具名被拒」「路径逃逸被拒」|
| 运行时| `pnpm verify:plugins`）6 条） | 直接驱动 `PluginHost`：工具*真的在子进程里执行了**。*环境变量确实被裁前*、错误路径不抛异常、停用后无残留进程|
| 集成 | `pnpm verify:renderer`）0 条中的12 条） | 通过真实应用：安装态→启用 →会话里确认*工具已注册给内核**。*插件技能已加载并进入系统提示* →停用 |

运行时那一层单独存在的理由：通过真实应用调用插件工具需要模型主动发起工具调用，
那依赖一个可用模型。而「插件运行时对不对」与「模型调不调它」是两件独立的事 ——分开验证，前者就不必被后者的前提卡住」


### 10.6 插件工具真的被模型调用过（这一轮补上的，
在此之前，「插件工具」这件事只验到*注册成功**：它出现在内核的生效工具列表里」那是必要条件，不是充分条件——中间每一段都可能断：

- 工具的schema 转不成厂商的函数调用格式（请求直接失败），- 模型的调用没被路由到插件子进程；
- 参数在转换里丢了，- 结果没回传给模型（下一轮模型只能瞎猜）。
它们失效时的现象都是「模型没调工具」，很难定位。所以这一轮让假模型*真的去调一次*：用户消息里带 `@fixture` 时，mock 改为发起 `fixture_echo` 调用（同一个mock 进程要同时服务两条路径，所以用消息内容而不是命令行开关来切换）。
一次跑通顺带验到：插件工具**也走审批**（它不在审批表里，按 `write` 风险处理）。参数原样到达插件进程、插件在自己进程里执行并一*拿不到宿主的敏感环境变量**。结果回传模型（收尾正文里带着插件的输出）。
#### 顺带抓到的真实缺陷：工具结果没有回写落盘

写完断言之后发现：*落盘的那条消息里，`tool-call` part 仍停在`pending`、没有结果*。
原因是时序：内核在工具*执行之前**就定稿了那条带tool-call 的assistant 消息，结果到达时只更新了内存里的live 状态，落盘的那份没人管。后果很具体 ——**重启应用后，那次工具调用永远显示「调用中」、也看不到结果*，用户会以为它还卡着「
这又是「一条消息有两个写入方」那一类（§5.5）：消息本体在定稿时写一次，
工具结果在之后写一次，而第二次在原来的设计里根本不存在「
修法：主进程在`tool.finished` 时调用`patchToolCallInSession(sessionId, callId, patch)`
回写落盘（按 `callId` 配对，因为一条消息里可能串行挂着多个调用）。防它的断言就叫「工具结果也回写到了落盘的消息（重启后不会停在「调用中」）」。

### 14.5 验证脚本自身的两个坑（都踩过，
打包验证的价值全在于「它真的验了」。而验证脚本自己出错时**表现是「通过」* ——这是所有测试里最危险的一种失败。两个实例：

**一、`verify:renderer` 曾经不构建就验「*
它只路E2E，不负责产出 `out/`。于是「忘了先构建」时，它测的是*上一次的产物**（代码明明错了，测试却是绿的。修法是让这个脚本*先构建再验*
（`build:deps && build && node scripts/verify-renderer.mjs`），
并且用「删掉`out/` 再跑一次」来证明这一步真的在起作用——**一个自举的验证脚本必须被证明能自举**，不能只看它写了什么命令「
**二、打包后的应用杀不干净」*
`child.kill()` 只杀掉了那个启动器，真正的`i-pi-desk.exe` 还在跑」后果是下一次启动时调试端口被占，测试连上一个*上一次的窗口** ——于是它验的是旧进程，而日志一切正常」修法有两半：清理由`taskkill /PID <pid> /T /F`（连子进程整棵树），
以及**启动前断言调试端口是空闲的** ——后者才是真正把问题挡住的那一半，
因为「杀干净」这件事本身也会失败」

## 15. 端到端验证：不接真模型也能验完整循环

`verify:renderer` 里有一整段「对话→工具调用 →审批 →工具执行 →结果回传 →收尾」，
**不接任何真模型*。做法是让mock 控制面*同时充当一个脚本化的假模型端点**

**二、驱动审批不能「先 await prompt 再处理审批」。*

### 15.1 没有时间上限的断言，验不出「卡住」
「中止」（Stop）是 agent 跑飞时唯一的出口，而它此前**一条断言都没有*。补的时候发现一个容易被忽略的点：它的实现里有一段很微妙的顺序要求——

界面上有一条预警：「本次运行已用N/M 步，接近上限」（阈值80%）。它的判定是纯函数、有单测，但**端到端一直没有覆盖* ——因为它此前*不可达*，
假模型一轮最多产用**2 次*工具调用，而2 次要落进 `[80%, 100%)` 需要`maxSteps ∀(2, 2.5]` ——**没有这样的整数*。
#### 2. 这一轮补的两件事

| 补什么| 怎么做| 为什么这样做 |
|---|---|---|
| 让「接近上限」变得可达| 假模型加 `@loopN` 连续工具调用模式 | 循环用`read` 而不是`write`：read **不需要审批*，于是这一段不必去点四次「仅允许这一次」，也就不会把审批路径的时序混进条| 
| 改maxSteps | **通过设置界面**改，而不是直接调 IPC | 预警读的是渲染层 store 里的 settings；直接调 IPC 的话 store 不知道，界面仍按 40 算，预警**永远不出现*（第一次跑就是这么红的，|

夹具的算例：**4 次工具调用+ `maxSteps=5` →4/5 正好 80%**。预警只在**运行为*显示，所以一边跑一边轮询（假模型每次循环刻意慢 400ms）。
#### 3. 排查过程中真正花时间的那件事：*假模型其实没被换掉*

新加的行为一直不生效（`@loop4` 不循环）。先后*怀疑并排除了*：假模型的循环代码「界面接线、设置同步。最后靠**把现场打出来**（让假模型记录它收到的最后一条用户文本）
