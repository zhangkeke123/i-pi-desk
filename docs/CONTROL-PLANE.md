# 控制面 HTTP 契约（桌面客户端 ↔ 管理服务）

> 本文是 `i-pi-desk` 桌面客户端与控制面之间的**接口契约**，可作为服务端实现的依据与验收标准。
> 参考实现（能跑的最小版本）：[`tools/mock-control-plane/server.mjs`](../tools/mock-control-plane/server.mjs)

## ⚠️ 先读：这份契约的适用范围

**服务端不在本仓库，也不在当前交付范围内。** 这里冻结的是「如果要接，接成什么样」。

两点必须清楚：

1. **PI-Desktop（上游）没有控制面，而且是明确决定不做的**（ADR 0004《No remote Gateway in the MVP》）。
   上游后来确实有远程能力，但那是 RACP（远程 agent 控制：SSH 到别的机器上跑 agent），
   与本契约的「登录 / 配置下发 / 技能分发 / 配额 / 审计」是两回事。
   本项目的客户端把它做成**可选且不在热路径上**的能力（见 `ARCHITECTURE.md` §9）。
2. **若为某个组织落地，认证应委托给该组织已有的认证中心**，不要自建用户名口令 ——
   否则等于在内网里新增第二个认证源，权限体系也会与既有 RBAC 对不上。
   `POST /api/auth/login` 的形状可以不变，实现做成一层转发即可。

---

## 0. 定位：控制面是「管理服务」，不是 agent 运行时

它只做四件事：**认证 / 配置下发 / 技能分发 / 审计与配额**。

agent 循环完全在桌面的本地 sidecar 里。这带来一条硬性质：

> **控制面离线时，桌面端的一切功能都必须照常可用** —— 包括对话、工具调用、终端、文件面板。
> 只是模型配置与技能停在最后一次同步的状态。

这条不是「最好如此」，而是设计约束：**任何一次 prompt 都不依赖控制面在线**。
实现侧也因此不需要为「控制面抖动」设计重试风暴 —— 桌面端只在三个时刻访问它：
登录、用户手动点同步、以及 run 结束后异步推审计。

## 1. 通用约定

| 项 | 约定 |
|---|---|
| 传输 | HTTP/1.1 或 HTTP/2，`Content-Type: application/json; charset=utf-8` |
| Base URL | 用户在桌面端填写，形如 `http://10.0.0.5:8080`（末尾斜杠会被客户端去掉） |
| 鉴权 | `Authorization: Bearer <token>`。**令牌不放 URL**（URL 会进日志、代理记录） |
| 超时 | 客户端 15 秒超时；超时按网络错误处理，不重试 |
| 401 / 403 | 客户端**立刻清掉本地令牌**并把状态置为未登录，提示重新登录 |
| 其它非 2xx | 按 `HTTP_ERROR` 呈现给用户，**不透传响应体**（可能含服务端内部细节） |

### 1.1 明文 HTTP

内网私有化部署用 `http://` 是常态，客户端**只警告不阻断**。
但如果目标是公网地址（非回环、非 RFC1918、非 `.local/.internal/.lan/.corp`），
客户端会在设置页显示醒目警告 —— 因为此时令牌是明文传输的。

**生产建议**：控制面放在内网，前置 HTTPS 终止（自签证书也行，客户端走系统信任链）。

## 2. 端点

### 2.1 `POST /api/auth/login`

```jsonc
// 请求
{ "username": "alice", "password": "secret" }

// 200
{
  "token": "…",                                  // 客户端存进系统密钥环，不进配置文件
  "user": { "id": "u-1", "name": "Alice", "roles": ["admin", "member"] }
}

// 401
{ "error": "invalid_credentials" }
```

**实现要求**

- **用户不存在与密码错误必须返回同一种响应**（都是 401 + 同一个错误体）。
  区分开等于对外提供一个枚举用户名的接口。
- `roles` 现在只用于显示。将来做「按角色下发不同技能」时，它会是第一个用到的地方。
- `name` 会被直接显示在设置页，请返回人类可读的名字。

### 2.2 `GET /api/config/models`

```jsonc
// 200
{
  "providers": [
    {
      "id": "cp-internal-vllm",              // 必填，且必须稳定
      "label": "内网 vLLM",
      "apiStyle": "openai-completions",      // 见下方枚举
      "baseUrl": "http://10.0.0.10:8000/v1",
      "models": [{ "id": "Qwen3-Coder-30B", "label": "Qwen3 Coder 30B" }],
      "enabled": true
    }
  ],
  "defaultProviderId": "cp-internal-vllm",
  "defaultModelId": "Qwen3-Coder-30B"
}
```

**`apiStyle` 枚举**（与 pi 内核的 api id 对齐；客户端会把 `openai-compatible` 归一成 `openai-completions`）：

`openai-completions` · `openai-responses` · `anthropic-messages` · `google-generative-ai` · `openai-compatible`

**实现要求**

- **`id` 必须稳定**。客户端按 id 做 upsert；每次登录换 id 会让本地堆积一堆失效 provider。
- **不要下发 API Key**。契约里没有这个字段，是刻意的：密钥应该由控制面**代理**请求，
  或者由用户在本地填（走系统密钥环）。让控制面把上游密钥发给每台终端，等于把密钥铺满全网。
- `baseUrl` 指向内网端点（vLLM / Ollama / 企业网关）时无需密钥，客户端也不会强制要求。

**客户端的合并语义（重要）**

同步时客户端**只替换 `source === 'control-plane'` 的 provider，用户手工添加的一个都不动**。
所以「控制面配错了一次」最多影响它自己下发的那部分，不会连带清掉用户本地的配置。

### 2.3 `GET /api/skills`

```jsonc
// 200
{
  "skills": [
    {
      "name": "cp-review-checklist",       // 必须符合 Agent Skills 规范
      "description": "代码评审清单。提交 PR 前使用。",
      "version": "1.2.0",                  // 可选，客户端目前只用于展示
      "content": "---\nname: cp-review-checklist\ndescription: …\n---\n\n# 正文\n"
    }
  ]
}
```

**`name` 的规范（会被客户端强校验）**

小写字母、数字、连字符；长度 ≤ 64；不能以连字符开头/结尾；不能出现连续连字符。
正则：`^[a-z0-9]+(?:-[a-z0-9]+)*$`

> 名字同时也是磁盘上的目录名，所以这条校验**同时**挡住了路径穿越（`../` 之类进不来）。

**`content` 是完整的 `SKILL.md` 文本**（含 frontmatter）。

- `description` **必填**：它决定模型会不会选中这个技能。写成「帮助处理 X」是没用的路由信息。
- 客户端**不会替你补 frontmatter**：自动生成的 description 一定是低质量的，
  与其凑一句不如让内容作者写清楚。

**实现要求**

- 不合规的技能名，客户端会**跳过并计数报给用户**（不会静默丢弃）。
  建议控制面在入库时就拦掉，别把问题留到终端上才暴露。
- 控制面删掉某个技能后，客户端会在下次同步时清掉本地那份 —— 但**只清它自己下发过的**，
  用户手工放的技能不动。这个「下发过哪些」的账由客户端自己记，控制面不需要维护。

### 2.4 `GET /api/quota`

```jsonc
// 200
{ "usedTokens": 128400, "limitTokens": 500000, "resetAt": "2026-11-01T00:00:00.000Z" }
```

`limitTokens <= 0` 表示不限量（客户端不画进度条）。`resetAt` 可选。

> **当前客户端只展示配额，不做本地拦截。** 超限拦截应当在控制面侧按上报的用量执行 ——
> 客户端拦截既不可信（用户可以改本地配置），也会在控制面离线时误伤。
> 若你希望桌面端也做软提示，可以约定一个 `exceeded: true` 字段，这是后续扩展点。

### 2.5 `POST /api/audit/events`

```jsonc
// 请求（批量）
{
  "events": [
    { "type": "run.completed", "sessionId": "s-1", "inputTokens": 120, "outputTokens": 40, "costUsd": 0.003,
      "at": "2026-10-10T05:37:52.000Z" },
    { "type": "run.failed", "sessionId": "s-1", "error": "…截断到 300 字…", "at": "…" },
    { "type": "tool.denied", "sessionId": "s-1", "toolName": "bash", "at": "…" }
  ]
}

// 200
{ "accepted": 3 }
```

**`type` 枚举**：`run.completed` · `run.failed` · `tool.approved` · `tool.denied`

**审计载荷的边界（请写进你的接口文档）**

> 只上报**用量与元数据**：发生了什么类型的事、哪个模型、多少 token、什么时候、失败了什么原因。
> **不上报对话内容与代码。**

这条边界是产品承诺的一部分。「审计」这个词很容易被理解成「把用户的东西都传走」，
所以它在契约、客户端注释、以及本文件里都写了一遍。

**实现要求**

- 必须是**批量**接口。客户端在 run 结束后异步推，控制面不可用时事件留在本地队列
  （上限 500 条）下次再试 —— 请不要设计成「一条一请求」，那会在网络抖动时放大成请求风暴。
- 返回值只要 `accepted` 计数即可。客户端**不清空未确认的事件**以外的任何东西。
- 建议做成幂等友好：客户端在极端情况下（发送成功但响应丢失）可能重发同一批。
  如果要做去重，可以约定客户端带上 `sessionId + at` 作为幂等键 —— 当前未启用。

## 3. 客户端行为速查（给联调时对照）

| 场景 | 客户端表现 |
|---|---|
| 未配置控制面 | 设置页显示登录表单；应用功能完整 |
| 登录失败 401 | 显示「用户名或密码错误」 |
| 令牌过期（任意接口 401） | 清令牌、状态转未登录、提示重新登录 |
| 网络不可达 | 提示无法连接 + 具体 URL；**本地功能不受影响** |
| 同步时技能名不合规 | 跳过并在结果里列出被跳过的名字 |
| 同步时多个 provider 同 id | 后者覆盖前者（按 id upsert） |
| run 失败 | 上报 `run.failed`（失败的留痕同样重要） |

## 4. 部署形态（对应你原方案的 P0 清单）

```text
员工桌面（i-pi-desk）
  · 本地优先；对话/工具/终端全部在本地
  · 登录控制面拿模型配置与技能；异步上报用量
        │ 内网 HTTPS
控制面（Java 单服务，部署在客户内网）
  · 用户认证（登录 / 角色 / 可选 LDAP 对接）
  · 模型管理（内网端点 + 可选的请求代理）
  · 配额（按上报用量统计；超限拦截在服务端）
  · 技能分发（上传 / 版本 / 下发）
  · 审计（用量与元数据）
        │
存储：PostgreSQL（随 docker-compose 起）
```

> 那份方案里「模型管理包含 API Key 托管」这一条，在本契约里**刻意没有下发密钥**。
> 如果你确实需要集中托管密钥，建议做成**服务端代理**（桌面端把 `baseUrl` 指向控制面的
> 转发端点，密钥只存在于服务端），而不是把密钥发给每台终端。前者一处失守，后者全网失守。

## 5. 验收方式

参考实现自带一份契约自测，**21 条断言**覆盖认证、鉴权、下发、配额、审计与「不泄露用户是否存在」：

```bash
node tools/mock-control-plane/verify-contract.mjs
```

Java 侧实现完成后，把脚本里的 `BASE` 换成你的服务地址即可当**对接验收脚本**使用。
另外 `pnpm verify:renderer` 会启动这个 mock 并驱动真实桌面应用走完整条链路
（登录 → 同步模型 → 同步技能 → **内核加载该技能并写进系统提示** → 配额 → run 失败 → 审计上报），
共 15 条断言。两边都过，才算接上了。
